PHASE 21 & 25 REMEDIATION FOLLOW-UP

Implemented and verified outside any numbered phase, per explicit separate approval of a reviewed remediation plan — no roadmap phase status changes as a result of this work.

- **Phase 21 — skip link doesn't move focus on most page templates:** RESOLVED. `tabIndex={-1}` added to all seven non-homepage `<main id="main-content">` elements (`about`, `error`, `experiences/[slug]`, `experiences`, `maasplassen`, `not-found`, `plan`) — two more than Phase 21's own enumeration, which tested content pages only; `error.tsx` and `not-found.tsx` share the identical gap. Verified: the skip link moves keyboard focus to `<main>` on every one, matching the homepage's existing pattern.
- **Phase 21 — mobile menu trigger unreachable by TalkBack:** NOT REPRODUCED in a retest on `/about`, performed after adding the LAN dev-server origin to `allowedDevOrigins`: with TalkBack enabled, TalkBack focused and announced the hamburger button; double-tapping it opened the mobile menu, and the menu links, language switcher, CTA, and close button were all confirmed reachable. The original Phase 21 finding stays on record as historical evidence (see CLAUDE.md's Accessibility section, unchanged) — this retest doesn't establish what the original result's cause was, only that it did not reproduce this time, on this route, under these conditions.
- **Phase 25 — `Header` has no error-boundary coverage:** RESOLVED. `app/global-error.tsx` added, rendering its own `<html>`/`<body>` and reusing `app/not-found.tsx`'s font-loading/styles pattern (the same true-root position). Verified by forcing a real error inside `Header`: the branded boundary rendered correctly (Deep Water background, Limestone text, Cormorant Garamond font all confirmed via computed styles), with normal pages unaffected afterward.
- **Phase 25 — error boundary used `reset()` instead of `retry()`:** RESOLVED. `app/[locale]/error.tsx`'s "Try again" button now calls `retry()`. Verified via a transient, counter-based forced error: clicking "Try again" caused the server component to genuinely re-invoke and render real content — the re-fetch behavior `reset()` doesn't provide.
- **Phase 25 — mobile menu could lose Tab position on an unrelated `Header` re-render:** RESOLVED. `closeMenu` in `components/Header.tsx` wrapped in `useCallback`. Verified by forcing a genuine Header re-render (crossing the `isScrolled` threshold) while the menu was open mid-Tab: focus stayed exactly where the user left it.
- **Phase 25 — `proxy.ts` matcher boundary, breakpoint-constant duplication, dead `not-found.tsx` metadata:** OPEN, unchanged. None implemented; each still needs its own separate approval, per the reviewed remediation plan.
- **Dev-environment finding, not from either phase:** real-phone testing against the LAN-bound dev server found that Next's dev server rejects cross-origin HMR requests from any non-localhost origin by default, leaving the client unable to complete hydration at all when loaded via a LAN IP — not a bug in `Header`/`Arrival`/`MenuButton`. RESOLVED via `allowedDevOrigins: ["192.168.0.191"]` in `next.config.ts` (dev-server-only, no production effect) — **this IP will need updating if the machine's LAN address changes**. Verified via real touch-tap events against the actual LAN URL: Arrival exits, the header un-suppresses, and the mobile menu opens and closes correctly both after entering and on an interior page loaded directly.
